# v1.3.2 · 接话链修复

## 修了什么

成员消息里同时出现 `@管理员` 和 `@佩丽卡 @庄方宜` 时，旧逻辑看到 `mentionsOwner` 就直接结束整轮，导致：

- 已经排定的旁听者不再回复；
- 同一条消息里被 `@` 的其他成员也不接话；
- 一次 `@` 多个人时，只可能走到其中一个。

现在：

- 成员提到 owner **不会**取消已经排定的初始回复（目标 + 概率旁听）。
- owner 和成员同时被提及时，先处理成员接话队列。
- 一次 `@` 多个成员会按提及顺序入队，每个成员一轮最多回复一次。
- `maxHandoffDepth` 与 `generationCap` 仍然限制总接话数。
- `replyTo` 指向真正触发这次接话的消息，而不是简单地指向上一条回复。
- 只有队列为空且最后一条仍只提到 owner 时，才以“交还 owner”结束。

## 诊断记录

实际群 `g_d1f846a1acc5` 的事件日志：

- 11 条 owner 消息，10 条成员回复。
- `2026-10-26T12:34:06Z` 有一条 owner 消息没有任何 `route` / 回复事件，可能当时进程重启或请求中断。
- `12:51:37`、`12:52:52`、`12:53:33` 的路由都包含祀 + 一位旁听者；祀的回复以 `@管理员` 开头，旧逻辑提前结束，旁听者被跳过。
- `12:53:51` 祀同时 `@佩丽卡 @庄方宜`，旧逻辑同样在 owner mention 处结束，两位成员都没接话。
- `12:54:48` 只路由到祀、没有旁听者，所以只有祀回复；这是 30% 旁听采样结果，不是 `@` 失效。
